# Architecture Rules

この文書は、機能追加によってコードベースが増築型・重複型になることを防ぐための設計原則を定義する。

## 1. 既存構造を優先する

新しい実装を作る前に、既存のcomponent / hook / service / repository / model / utility / APIを検索する。

再利用可能なものがあるなら再利用する。

## 2. 概念を増やさない

同じ意味のものを別model・別service・別APIとして作らない。

名称が違っても責務が同じなら統合可能性を検討する。

## 3. ドメインとUIを分離する

UIコンポーネントに本質的なbusiness logicやdata accessを大量に持たせない。

UI変更によってdomain logicが壊れる構造を作らない。

## 4. Business logicを一箇所にする

同じルールを複数の画面でコピー実装しない。

## 5. データアクセスを集約する

画面ごとに直接DB/APIへアクセスする構造を乱立させない。

既存のdata access boundaryがある場合はそこを利用する。

## 6. 共通概念を共有する

スポーツが増えても、スポーツごとに同じ構造をコピーしない。

例えばサッカー、バスケットボール、バドミントン等が追加されても、共通のSport / Opportunity等で扱える部分は共有する。

スポーツ固有の属性が必要になった場合だけ、明示的な拡張方法を検討する。

## 7. Opportunity中心の拡張

募集・参加機会は、可能な限り共通モデルを基盤にする。

種類が増えるたびに別バックエンドを作るのではなく、共通部分と種類固有部分を分離する。

## 8. TeamとUserを混同しない

Userは個人アカウント。

TeamはUserが作成・管理するエンティティ。

Team専用アカウントを作らない。

## 9. 新しい抽象化は必要になってから

将来使うかもしれないという理由だけで巨大なframeworkや抽象層を作らない。

ただし、明らかな重複を放置してfeatureごとのコピー実装を続けることも禁止する。

## 10. 変更の影響を考える

新しい変更が既存機能へ与える影響を確認する。

特に以下を確認する:

- DB
- API
- authentication / authorization
- navigation
- shared state
- notification
- caching
- existing screens

## 11. エラーを隠さない

禁止:

- `any`による型エラー隠蔽
- 空catch
- 意味のないdefault値
- silent failure
- TODOで未実装を隠す

問題は根本原因を修正するか、Leaderへ報告する。

## 12. 将来の追加を想定する

設計判断では、同じカテゴリの機能が今後複数追加されることを考える。

ただし「未来の全て」を予測して過剰設計しない。

**現在必要な共通構造を綺麗に作り、将来の拡張点を壊さない。**
